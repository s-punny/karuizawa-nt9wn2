## 悩んだ点・捨てた案

- **「仮」マーカーの見せ方**。最初は枠線付きのバッジ（0.5px border + padding）にしたが、
  タイムラインの注記など小さい文字に付くと潰れて「読めない小さな箱」になった。
  枠を捨てて、金の下線＋9px固定の「仮」の文字だけに変更。em指定をやめてpx固定にしたのがポイント。
- **`.tbd` をブロック要素に直接付けた問題**。`<dd class="tbd">` のようにすると
  ハイライトの下線がグリッドのセル幅いっぱいに伸びた。中身を `<span>` で包む方式に統一。
- **`text-transform:uppercase` を日本語混じりのラベルに当てて「新婦FAMILY」になった**。
  英字コード（Route A）と日本語ラベルを別spanに分離して解決。以降、和欧混在のラベルは分ける方針に。
- **Cormorant Garamond の既定がオールドスタイル数字**で、日付の「10」が「IO」に見えた。
  `font-variant-numeric: lining-nums` を body に。時刻表記が多いページなので影響が大きかった。
- **参列者全員に「仮」バッジを付けたらノイズだらけになった**。全員が未確定なら個別に印を付ける意味がない。
  バッジを外して「お名前は仮置きです」の注記1行に置き換え。
- **全体を暗色にするか**で迷った。大人っぽさ＝暗い、と短絡しかけたが、
  表紙と奥付だけ濃色・中面は紙色、という冊子のリズムに落ち着けた。全面暗色は読む文書として重い。
- **前撮り写真がない**という制約。ユーザーから「軽井沢の風景やチャペルの感じなら入れられる」と聞き、
  「写真がなくても成立し、置けば差し替わる」設計にした。
  画像が無ければJSで `<img>` を除去してプレースホルダのまま残す（壊れた画像アイコンを出さない）。
- **公開方法**。GitHub Pages の無料プランは、リポジトリを private にしてもページ自体は公開される。
  このページには両家の氏名・電話・宿泊先・**当日自宅が留守になる日付**が載る。
  パスワード保護のために Cloudflare Pages / Netlify に移す案も出したが、
  検索避け（noindex + robots.txt）＋推測されにくいリポジトリ名（`karuizawa-nt9wn2`）で十分と判断して見送り。
  リポジトリ名から `wedding` `invitation` を排除したのはそのため。
- **地図の実装**。APIキーが要る Maps JavaScript API ではなく、`output=embed` のiframe方式。
  住所が決まったらURLの `q=` を書き換えるだけで済む。色は grayscale + sepia でページの色域に寄せた。
- **「全部やって」に対してどこまでできたか**。gh CLI が未インストール、
  Chrome操作は権限で拒否、トークンを預かるのは方針として不可。
  結果「空リポジトリの作成だけ手動、それ以外は自動」に落として提示した。

## 学び・気づき

- Git Credential Manager に GitHub の資格情報があれば push は非対話で通る。
  `credential.helper` は global が空でも system 側（`C:/Program Files/Git/etc/gitconfig`）に `manager` が入っている。
- GitHub Pages は main に push しただけでは有効化されない。Settings → Pages での設定が必須。
  （`gh-pages` ブランチによる自動有効化を期待したが、今回は発生しなかった）
- `og:image` は絶対URLでないと LINE がサムネイルを取得しない。相対パスだと無言で無視される。

# 2026-08-02（第4セッション）高解像度の写真で表紙と見開きを作り直し

## やったこと

- 1000×650 のチャペル写真2枚を受け取り、写真まわりを組み直した
  - `images/cover.jpg`（正面外観）＝ **表紙の背景**。grayscale(.88) + contrast(1.12) + brightness(.82) に
    墨緑のかぶせ（放射＋線形グラデーション3枚）を重ねて沈める。ケンバーンズは 30s に緩めた
  - `images/chapel-nave.jpg`（内観・身廊）＝ ごあいさつ直後の**見開きの主写真**
- 写真帯を「見開き」に作り直し（デザイナー感の実装）
  - 左に**縦組みのキャプション2本**（欧文 THE CHAPEL ／ 和文）、右に主写真を**右へ断ち落とし**
  - シャンデリアの一枚を主写真の**左下に重ねる**（紙色の outline でマット、影は 44px の低コントラスト）
  - 重ねは絶対配置ではなく「2行グリッド＋負の margin-top」。行が分かれるのでキャプションと衝突しない
- 表紙に**罫の額**（内側 hairline ＋ 左上/右下の真鍮のコーナー）を追加
- 表紙に写真が載ったときは**稜線SVGを消す**（`.cover.has-photo .ridge{display:none}`）。
  写真と稜線が重なると絵が濁るため。JS の画像ロード成功時に `.cover` へ `has-photo` を付与
- 挙式会場カードの写真を、外観（540×400）に変更
- 低解像度の `chapel-interior.jpg`（280×200）は、同じ室内をより良く写した `chapel-nave.jpg` に
  置き換わったため削除

## 悩んだ点・捨てた案

- **縦組みキャプションを右に置いたら主写真とぶつかった**。右へ断ち落とす以上、右側にテキストは置けない。
  キャプションを左、写真を右へ、という当たり前の配置に戻した。最初から絵を描いて考えるべきだった。
- **重ね写真を絶対配置にしたら、キャプションの下に潜り込む可能性**があった。
  `position:absolute` をやめて2行グリッド＋負マージンにしたことで、行が物理的に分かれて衝突しなくなった。
- **スマホで縦組みは幅を食いすぎる**。390px 幅で縦書き2本＋写真だと写真が潰れ、下に巨大な空白が出た。
  720px 以下では横組みに戻し、「主写真（右へ断ち落とし）／下段に重ね写真＋横組みキャプション」に変更。
- **表紙の写真をどこまで見せるか**。最初 opacity .40 では建物が主張しすぎて文字が読みにくかった。
  .46 に上げたうえで brightness を .82 に落とし、中央だけ明るさを残す放射グラデーションで
  「名前の背後がいちばん静か」になるよう調整した。

## 学び・気づき

- **このコンテナには IPAGothic しか日本語フォントが無く、縦組みの漢字が重なって描画される**。
  かなは正常。つまりスクリーンショット上の縦書きの崩れは環境の問題で、実機（Shippori Mincho B1 が
  Google Fonts から読まれる）では再現しない。切り分けに最小の HTML を1枚作って確認した。
  **ヘッドレスの見え方を鵜呑みにしない**、というのが今回いちばんの学び。
- 重ね合わせのレイアウトは、絶対配置より「グリッドの行を分けて負マージン」の方が壊れにくい。
  兄弟要素との衝突を、z-index ではなくレイアウトのレベルで防げる。
- 写真を敷いたら、それ以前に置いていた装飾（稜線SVG）は引く。両方出すと必ず濁る。

## 悩んだ点・捨てた案

- **丸の位置ずれの直し方**。`li::after` に `top:1.55em` で置いていたため、em が li の
  文字サイズで解決され、挙式行だけ文字が大きい（1.3rem）と丸が行の中心からずれていた。
  丸を**時刻セル `.t` の擬似要素に付け替えて**、`top:calc(.16em + 1.025em - 5px)`
  （padding-top ＋ 行送りの半分 − 半径）とした。em が時刻の字送りで解決されるので、
  行ごとに文字サイズが変わっても中心に乗り続ける。8行すべて X=177.55px で一致を確認。
- **段の幅を直値で3か所に書いていた**のが事故の元だった。罫線・グリッド・丸が
  それぞれ `4.6em` を持っていて、余白を足すと全部ずれる。`--col` 変数にまとめた。
- **表紙の「洗練されていない」をどう解くか**。装飾を足す方向ではなく、**要素を減らす**
  方向で解いた。縦書き・地名・額・スクロール表示を全部外し、
  「日付 → 短い罫 → 名前 → 和名 → 会場」の一軸だけに絞った。
  中央ぞろえをやめたのがいちばん効いた。左ぞろえにすると軸が1本になる。
- **SCROLL表示の置き場所**。右下・右端中央と試したが、本文が左下にあるので
  どこに置いても「浮いた1本の線」になる。**消すのが正解**だった。
  スクロールできることは見れば分かる。
- **もらった外観写真（540×400）を表紙にできるか**を検証して見送り。
  - スマホの表紙は 1170×2532 相当なので **約6.3倍の拡大**になり、板張りの質感が潰れる
  - 横長4:3を縦長画面に敷くと**横幅の3割しか映らない**。中心を 34% に寄せて塔は
    入れられたが、この写真の良さ（木立に囲まれた全景と青空）が全部切り落とされた
  - 「切り取った瞬間に、その写真を選んだ理由が消える」。式場に元データを依頼する方針に
- **`.note` に段落を3つ入れたらグリッドの左列に落ちた**。`.note` は
  `grid-template-columns:8.5em 1fr` で、子が h3 + p の2つ前提だった。
  4つ入れると3つ目が次の行の左列（見出し用の8.5em）に入って潰れる。
  本文を `<div>` で1つに包んで解決。**「子要素は必ず2つ」という前提が
  CSSに書かれていない**のが原因なので、`.note p + p` の余白も併せて定義した。
- **カードが1枚だけになると `.duo` が1カラムになり、写真が引き伸ばされる**問題。
  ご宿泊を1カードにしたら hotel.jpg（600px）が860px幅で表示された。
  地図を別カードに分けて2カラムを保った。写真の元データが小さいときは
  **レイアウトの列数で表示幅を制御する**のが手っ取り早い。

## 学び・気づき

- 「〇がずれている」のような指摘は、たいてい**単位の解決先**が原因。
  em を使うなら、それがどの要素の font-size で解決されるかまで見る。
- 表示サイズを決めるのは CSS の幅指定だけではなく、**グリッドの列数**でもある。
- 写真の使えるかどうかは「解像度」と「構図が切り取りに耐えるか」の**2軸**で見る。
  解像度が足りていても、縦長画面への全面敷きは横を7割捨てる。
  正面・左右対称の写真（いまの cover.jpg）はこの切り取りに強い。
